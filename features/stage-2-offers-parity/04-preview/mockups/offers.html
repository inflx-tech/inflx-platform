Four places, two dates, and a warning that tells the truth.
The dates already work. store_starts_at and store_ends_at exist, the API accepts them, and checkout already refuses an offer outside them — both ends, in transaction.controller.js. The shopper app already shows the end date. Nothing sets them. This adds the missing entry point, not the rule.
⚠️ Worth knowing: web does not have this either. Its builder saves { name, offer_type, offer_config_json, availing_modes } and no dates. So "match web" would still leave this missing — the founder asked for more than parity here, and he was right to.
And a smaller gap this closes. POST /brands/me/offers does not accept the dates at all — only PATCH does. So today a validity window could only be added by editing an offer after making it.
Where a shopper can use it is availing_modes. It exists, web sets it, the phone never has — so a phone-made offer silently falls back to the database default of pay-at-store and online. Both production offers show exactly that.
