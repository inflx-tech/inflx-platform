# Workflow prediction — ui-walk-fixes
Trigger: a brand or a creator uses the screens they already have. End state: the same work gets
done with the same data, on screens that show more and hide less. A new set has the name its brand
typed. The creator list has the phone, not the bars. The box being typed in is always in view.
Deliverables are one line each. Choices side by side are level. A thing to tap looks like a button
and says what it does; a thing being waited for looks like a status and says who is waited for. The
brand who sends an agreement reads "Waiting for her to sign by …" and can reopen or withdraw it.
Date and time are two boxes. A content file opens inside the app. A pasted link is saved without
being asked and the "posted" button turns on.

No row is stored differently, no status means something new, and no money moves. One server answer
changes: after a brand withdraws an agreement, the creator's row comes back as "Your move — Send
agreement" instead of a row with no way forward.

Edges: a brand used to accepting "Set A" must now type a name · a creator open to five things shows
"+2" on the compact row · a small phone (640 tall) with the keypad open still shows the focused box
· all five deliverable types added (no "+ Add another") · agreed visit time already passed (Move
sheet opens empty) · an app build older than 30 Sep (video falls back to the browser, photos still
open inside) · a link pasted without "https://" · two links saved one after the other with answers
arriving out of order (both stay filled) · a Send refused because the signing date passed.
