# C11-live-link-button-disabled — "I have posted everything" stays disabled after pasting link

## TODAY
Creator app, after the brand approves her content. Two screens share the same behaviour: "Your content" (Pay for Content) and "Going live" (Pay for Sale and Hybrid).

Top to bottom on "Your content": back arrow + title; small grey crumb "BRAND · SET A"; a green box "Approved on 22 Oct. Post it now — this is the version they approved."; heading "Add a link for each one"; then one white card per deliverable (e.g. "Instagram reel" with a small grey count chip "0 of 1" on the right). Inside each card is one plain bordered text box per post she owes, with the grey placeholder "Paste the link". A Story card shows a dashed "+ Add" tile for a screenshot instead. Pinned at the bottom of the screen: a grey (disabled) button "I've posted everything" and under it a small grey line such as "1 link to go."

What happens when she pastes: the link text appears in the box. Nothing else changes. No tick, no "saved" sign, no Save button, the count chip still reads "0 of 1", the bottom line still reads "1 link to go." and the button stays grey. Tapping the grey button does nothing. If she hides the keyboard with the phone's back gesture the box still counts as "being edited", so the link is still not sent, and on Android 11 and newer tapping blank space no longer rescues it. The only ways to make it work are: tap the Done/Go key on the keyboard, tap into a different link box, or tap blank space while the keyboard is still showing. Once one of those happens the link is sent, the chip turns green "1 of 1", the "to go" line disappears and the button turns black.

If INFLX refuses the link (it does not start with https://, or it is not from the platform that row is for, e.g. a YouTube link on an Instagram reel row), a small red line "Paste the full link to the post." appears under the box and the button stays grey. That red line never appears in the paste-and-wait case, because nothing was ever sent.

"Going live" (Pay for Sale / Hybrid) is the same inside the "Social media" card: one "Paste the link" box per row, same grey bottom button and "1 link to go." line. The "Where did you share it?" block for posts shared outside the package has the same paste box and no Save button at all.

## ROOT CAUSE
The button's on/off state comes only from the server (`disabled={!c.can.markPosted}`), and the server sets `markPosted` true only when every proof slot has a saved row (`slots.every(x => x.filled)`). The only code that saves a link is `saveLink()`, and it is wired solely to the TextInput's `onEndEditing`. On Android `onEndEditing` fires only when the field loses focus. A paste fires `onChangeText` only, which writes to local state (`links[key]`) and makes no API call. So after a paste: no PUT /content/proofs/:rowKey/:slot, `c` is never refreshed, `can.markPosted` stays false, `proofsLeft` still lists the slot.

Why it feels permanently stuck rather than a one-tap delay: (1) the bottom bar is outside the ScrollView and the button is a disabled TouchableOpacity, so tapping it neither blurs the field nor does anything; (2) hiding the keyboard with the Android back gesture does not blur a TextInput; (3) the ScrollView uses keyboardShouldPersistTaps="handled", and React Native 0.73 only blurs on a blank-area tap while it believes a keyboard is open (`_keyboardIsDismissible`, which on Android API 30+ is false once the keyboard is hidden), and never on a scroll drag; (4) with a single deliverable there is no second field to tap into. There is no Save control and no saved-tick, so the screen gives no clue.

Secondary cause (real, but not what a normal pasted share link hits): the server's `validLink` accepts only `https:` links whose host is on the row's platform list and whose path is not empty. Normal share links pass (www.instagram.com/reel/...?igsh=..., youtu.be/...?si=..., youtube.com/shorts/..., m.youtube.com, facebook.com/share/..., fb.watch; trailing spaces/newlines are trimmed on both ends). Refused: a link with no "https://" in front (exactly how the locked board draws them, "instagram.com/reel/C8xK2…"), an http:// link, a link pasted together with other words, and a link from the wrong platform for that row. All of those return the same generic sentence "Paste the full link to the post.", which does not tell her which of the four it was.

Ruled out: there is no date gate, posting-date gate or offer-active gate on saving a link or on "I've posted everything" (contentGate + setProof + markPosted checked); the only other blocks are the collaboration being frozen by a brand report, or the stage not being "approved". The round-trip after a successful save is correct: the PUT returns the full fresh content and the screen applies it (`setC(r.data.content)`), so once the save actually runs the button does enable.

## CORRECTIONS
- Certainty overstated: the mechanism is proven from code, but whether the founder hit 'never sent' (no red line) or 'sent and refused' (red line 'Paste the full link to the post.') cannot be determined from code. Both leave the button grey. Refusal path: backend/src/services/contentFlow.service.js:568-577 and 606-607; never-sent path: Packages/Mobile/src/screens/influencer/ContentScreen.js:298-300.
- Caption risk understated. The caption boxes are multiline (ContentScreen.js:249-251, SaleLiveScreen.js:330-332); for multiline inputs React Native's default is that the Return key inserts a new line and does not leave the box (node_modules/react-native/Libraries/Components/TextInput/TextInput.js:1363-1368). So a caption has NO keyboard-key way to save, only leaving the box. The package is built from server-saved captions only (backend/src/services/contentFlow.service.js:454-456) and the send sheet lists only file counts, not captions (Packages/Mobile/src/components/content/sheets12.js:27-31), so the loss is invisible to her.
- Why the Done key works was not shown by the investigator: no screen in the app uses onSubmitEditing at all (grep of Packages/Mobile/src returns none); it works only because a single-line box defaults to blur-on-submit (TextInput.js:1369-1375) and Android sends end-editing on blur (ReactTextInputManager.java:1087-1100, 1132-1133). Confirmed, but it is implicit behaviour, not written in the screen.
- The 'back gesture does not leave the box' statement is correct but was uncited: ReactEditText.java has no onKeyPreIme/back-key handling (grep returns only clearFocusFromJS at line 629).
- 'Build the Save link button exactly as locked on S17' does not fit the built app. S17 is drawn as its own screen with a pinned bottom button. The app renders outside-package rows inline inside Going live (SaleLiveScreen.js:420-452), the pinned bar is already used by 'I've posted everything' (465-470) and 'Ask INFLX' (471-473), and outside rows are open from the first send onward, including during the approved stage (backend/src/services/saleLive.service.js:410). A pinned 'Save link' would collide with 'I've posted everything', and there can be several outside rows.
- 'Per-field sequence number' is not enough to make auto-save safe. Every save replaces the whole screen state with the reply (ContentScreen.js:150, SaleLiveScreen.js:198) and deletes the local text for that box (ContentScreen.js:149, SaleLiveScreen.js:197). Two different boxes saved close together can get replies out of order: the older reply overwrites the newer, and a box whose local text was already cleared shows empty although the server has the link. Needs one in-order queue per screen (or a screen-wide 'latest reply wins'), and the local text must be cleared only if it still equals what was sent.
- 'Only auto-save when the text parses as a link on a known host' would require copying the server's host list (backend/src/services/contentCopy.js:169-174) onto the phone. Nothing keeps such a copy in step: the word-for-word test covers only refusal sentences (Packages/Mobile/src/components/content/__tests__/content12.test.js:10-22). Let the server judge instead and only hold back the red line while she is still typing.
- New phone-only sentences ('Saving your link…', 'One link needs fixing — see above.') must go in C12 / C14, NOT in MSG12: content12.test.js:13-21 fails for any MSG12 key that the server's MSG does not have with identical text.
- Adding 'https://' on the phone is described as 'without touching the server rule', but the creator app is the only client, so it has the same effect as loosening the approved rule that backend/tests/item12-flow.test.js:263-267 asserts ('instagram.com/reel/x' refused). It is a founder decision either way, not a free technical tidy-up.
- Board numbering trap: the code and tests label these moments one number lower than the locked board. SaleLiveScreen.js:359 says 'S14 — approved', 386 'S15 — posted', 419 'S16 — outside'; saleLiveScreens.test.js:117 'S14, S15'; copy14.js:77 and 88. The board itself (item14-sale-going-live-mockups-v2.html) calls them S15, S16, S17, as the finding says. Also the board's S15 header title reads 'Share on social' while the app shows 'Going live' (Packages/Mobile/src/components/sale/copy14.js:18) and puts this block as a card inside the Going live screen.

## FIX RISKS
- Out-of-order replies across DIFFERENT boxes can blank a saved link and switch the button back off (whole-screen state replaced per reply, local text deleted on success). A per-field counter does not prevent it; saves must be queued in order.
- Auto-save while typing can eat characters: if she keeps typing after a save was sent, clearing the local text on success snaps the box back to the older server value. Clear only when local text equals what was sent.
- Debounced save plus save-on-leave plus save-on-Done can fire two or three identical requests; harmless on the server (upsert) but each returns a full heavy read and they can interleave. De-duplicate against the last value sent.
- A paste followed immediately by Back (inside the pause) loses the link unless pending saves are flushed on leaving the screen; the screen's 'mounted' guard (ContentScreen.js:53-56) will also drop the reply.
- Typing a link by hand with auto-save can store a half-typed but valid-looking link (the server checks shape only, e.g. https://www.instagram.com/reel/C passes), turning the chip green and the button on early. Final value still saves on leave/Done, so the end state is right, but the button can enable on a truncated link if she stops there.
- Fix B makes the phone decide when the button is tappable. That departs from the screen's own written rule that the moment 'comes from the server's stage and can, never from a guess on the phone' (ContentScreen.js:5-7, SaleLiveScreen.js:11) and from the locked boards C10/S15, which draw the button disabled with the 'to go' line. Money and state stay safe because the server still refuses with PROOF_INCOMPLETE (contentFlow.service.js:640), but it is a visible change that must be drawn and locked first.
- A pinned 'Save link' button per S17 collides with 'I've posted everything' in the same bar during the approved stage, and with 'Ask INFLX' during posted; with several outside rows a single pinned button is ambiguous.
- Do not edit PrimaryButton itself (Packages/Mobile/src/components/settings/primitives.js:118-145): it is used across the whole app in both apps. Change only what these two screens pass to it.
- Jest: the two existing screen tests (contentScreens.test.js:142-154, saleLiveScreens.test.js:117-127) keep passing only if an empty box still shows grey button + 'to go' line. New tests with a timed pause need fake timers; the suites currently run on real timers with waitFor.
- content12.test.js:13-21 will fail if any new sentence is added to MSG12 instead of C12/C14.
- Backend contract is untouched by A+B, but phone-side 'add https://' silently changes the outcome of an approved rule that a backend test pins (item12-flow.test.js:263-267). Needs the founder's explicit yes.
- No native rebuild needed: Keyboard is core React Native, and the clipboard module is already in the installed app (Packages/Mobile/package.json:19, used by OTPScreen), so even an optional 'Paste' button would ship over the air. Detect a paste by the text jumping in one change rather than adding any new native package.
- Other app: brand behaviour does not change, but the brand bundle includes SaleLiveScreen.js and bits12.js, so the next brand OTA carries the edit; run the brand screen tests too.
- Process gates: this touches Packages/Mobile/src, so it needs its own contract with a locked board (gov-check Rule 3), before/after notes (Rule 4) and maestro_green for release (Rule 5). The item12 and item14 contracts are already released; do not piggy-back without recording it. There is no Maestro flow covering these screens today (no match under qa/).

## FIX FINAL
One over-the-air update to the creator app. JS only: no server change, no migration, no new app install.

1. One shared link box (new, additive piece in Packages/Mobile/src/components/content/bits12.js) used in all three places: ContentScreen.js:298-300, SaleLiveScreen.js:375-377 (package rows) and 432-434 (outside rows). It shows 'Saving…', then the board's tick when INFLX has the link, or the red line when refused. The server stays the judge of what is a valid link; do not copy the host list to the phone. Hold the red line back while she is still typing.

On press: close the keyboard, finish the queue, and only if every link was accepted send 'I've posted everything'. If one is refused, stop and show the red line on that row. Outside-package rows never count toward this button. New sentences live in C12 and C14, never MSG12.
