1.3–1.5 Registration (3 actors, 3 very different paths)

Brand — web only

POST /brands/register
  • business_name, category, name, city, state, address, pincode
  • city+state live on users, not brands
  • 409 on duplicate
  • stays pending → admin review

Influencer — mobile only

POST /influencers/register
  • name, instagram_handle (req), city, youtube
  • Apify scrape seeds followers/ER/niche
  • creator-profile claim: 1 match→claimed, >1→admin conflict, 0→stub
  • stays pending → admin review

Follower — auto-approved

Followers are approved at verify-otp — no admin review. POST /followers/register is just idempotent profile completion (name/city/state), not a gate.

1.6 Admin Login + RBAC A

Admins pre-provisioned by a superadmin. 3 sub-roles, enforced server-side.

superadmin
everything

approval queue

requireAdminRole(x): superadmin always passes; reviewer/finance pass ONLY their exact domain (not interchangeable). requireAnyAdminRole: any admin.

⚠️ Drift: admin-web sidebar shows ALL nav to every admin; admin_role isn't in the client user object. Enforcement is 100% server-side (a reviewer clicking Payouts gets API 403, not a hidden link). Not a security hole — UX polish.
